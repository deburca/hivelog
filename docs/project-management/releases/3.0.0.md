# Release 3.0.0 (planned)

Apiary roles. Every member of an apiary now has a role that decides what they may do, and access comes
from that membership alone. This is a **major** release because it changes what existing members can do,
renames the stored roles and moves access off the apiary's `uid` field.

## Highlights
- **Three ordered roles: novice < beekeeper < owner** (task 0224). A novice reads everything and changes
  nothing. A beekeeper can do every action on the apiary and its hives except manage members and owners,
  edit the apiary's own settings (the apiary edit form: name, location, map, notes, visibility and the
  AI-insights consent) and delete the apiary. An owner can do all of it. The three access checks
  (view, edit, owner-only) in `ApiaryAccessTrait` now read the role; the creator-based "delete your own
  record" rules are gone, so a previous owner or member keeps no right over what they once created.
- **Several owners.** Owners are the memberships with role `owner`. Handing an apiary over is "A adds B as
  owner; later B removes A". Owners may remove other owners; the last owner cannot be removed, or given
  another role.
- **`uid` is history only.** The apiary's owner field ("created by") no longer grants access and is gone
  from the edit form. A new apiary's creator gets an `owner` membership automatically.
- **A new operation, `write`,** on the apiary ("may add or change records inside it": beekeeper and
  above). The scoped add routes (hive, calendar action, action log, inventory item, purchase, product,
  sensor device) and the parent-access rule use it; `update` stays the apiary's own settings, owner-only.
- The site-wide "own" permissions keep their meaning: the apiary role and the site permission must both
  allow. A non-member on a public apiary still reads it.
- The API goes through the same handlers, so an app token acts with its user's role (a novice's token is
  read-only); the field-app role is unchanged.

## Upgrade notes
Run `drush updb` and `drush cr`. `hivelog_update_10035()` does two things, and is safe to run twice:
1. **Renames the stored roles:** `viewer` becomes `novice` and `editor` becomes `keeper`. Members that
   hivelog 2.x migrated from the old `beekeepers` field were `viewer`, and could edit everything before
   roles were enforced; **they now become novices and can read only.** Promote anyone who should keep
   editing to Beekeeper on the apiary's edit page (Members) after upgrading.
2. **Gives every apiary's current owner an `owner` membership** (an existing membership of theirs is
   promoted), because access no longer comes from `uid`.

Other things that change:
- Adding a member still needs the `add apiary membership` permission; the add, edit and remove routes also
  need `edit own apiary` and an owner role in that apiary.
- A beekeeper can now add hives, calendar actions, inventory and so on, which only an owner could before.
