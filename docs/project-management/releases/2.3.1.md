# Release 2.3.1

## Highlights
- **Fix: reversed and malformed From/To ranges in filter forms (task 0169).**
  A "From" later than "To" used to be applied as two independent conditions
  and silently matched nothing, and a malformed date in a hand-edited query
  string went straight to the query. A new shared helper,
  `HivelogRangeFilter`, now decides what happens, the same way everywhere:
  - a date that isn't a real `YYYY-MM-DD` day is **dropped**, and a notice
    above the filter fields says so;
  - a reversed pair is **swapped** (what Calendar Actions' week range always
    did), and a notice says so.
  - Applied to **Inspections**, **Queen Observations**, **Inventory
    Purchases**, **sensor readings** (nanoprobe) and **Calendar Actions**
    weeks. Calendar Actions already swapped silently, but its form kept
    showing the reversed values the user typed, so the fields and the
    results disagreed.
  - The From/To fields now show the *corrected* values, so after a swap they
    no longer echo what was typed.
  - The notice only appears when something was corrected, is announced as a
    status message, and is a new `.hivelog-filter-form__notice` style using
    the existing warning tokens.
- **Docs.** AGENTS.md now says a From/To filter must use `HivelogRangeFilter`.

## Upgrade notes
- No breaking changes, no data migration.
- `ddev drush cr` after upgrading, so the new notice style is picked up.
- If a theme overrides `css/hivelog.filter-form.css`, it won't have the new
  `.hivelog-filter-form__notice` rule; the notice still shows, just unstyled.
- `SensorDeviceController::extractValidDate()` (protected) was removed in
  favour of `HivelogRangeFilter::isValidDate()`. A site subclassing that
  controller and calling it would need to switch.
