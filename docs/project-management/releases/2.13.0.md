# Release 2.13.0

Editing and deleting for the Vinculum app (task 0220): an app token can now change a saved inspection or
queen observation (and its photos) even through a web host's firewall, and can delete its own inspections and
queen observations. Only matters on a site that has enabled the optional `hivelog_api` submodule; nothing
changes without it.

## Highlights
- **A firewall that refuses `PATCH`, `PUT` and `DELETE` no longer stops the app editing.** The live host
  (`kragebaekgaard.dk`) answers a bare `403` to all three, whatever the content type or headers, before
  Drupal sees them (probed 2026-10-15), but lets a `POST` with `X-HTTP-Method-Override` through. On
  `/hivelog/api/v1`, a `POST` that carries an `Authorization` header and `X-HTTP-Method-Override: PATCH`
  or `DELETE` (any case) is now run as that method, with the same content-type relaxation as 2.11.0's
  `application/json` writes. JSON:API, access, validation and the field-app role's ceiling treat it as the
  real `PATCH` or `DELETE`, so the override grants nothing a real one would not.
- **Symfony already honours that header on any POST, for any method.** The change narrows it on the
  versioned prefix: any other value, a request with no `Authorization` header, and the plain-JSON routes
  (`computed/`, `schema`, `sign-out`) have the header removed and the method reset to the plain `POST` they
  really are. Drupal's own request sanitiser already answers 400 to an override to a safe method. Off the
  prefix (`/jsonapi`) nothing changes. Advertised as the `method_override` feature in the discovery document
  (`meta.hivelog_api.features`), so an app uses it only when offered; `api_version` stays 1.
- **The app role may delete its own inspections and queen observations, and nothing else.** The
  `hivelog_field_app` role gains `delete own hive inspection` and `delete own queen observation` (until now it
  held no `delete` permission at all, ADR-0107 section 4). Both are leaf records: deleting an inspection only
  detaches the action logs that pointed at it, and an observation has no children. Apiaries, hives, queens,
  calendar actions and action logs stay undeletable by an app token. The access handlers still decide who may
  delete which record, exactly as on the web: an apiary's owner may delete any inspection in it, a member
  only the ones they created, an outsider nothing.
  `hivelog_api_update_10004()` adds the two permissions on an existing site and never revokes a change a
  site made.
- **Photos of a deleted record, and of a removed image, are left as the web leaves them.** Both surfaces use
  the entity's own delete, and both leave the file permanent and unused (Drupal only makes an unused file
  temporary if the site turns on `make_unused_managed_files_temporary`, off by default). Removing a photo is a
  `PATCH` of the record's `images` relationship, which leaves the file likewise. No clean-up was added: that is
  a site-wide policy, not something the app's delete should change. A client that resends the images it
  keeps must send each photo's `meta` (alt text and title) back, or the server wipes them.
- **A refused delete says why where the web does.** A refusal for a record with children (BLOCK, ADR-0103)
  carries the reason in the error's `detail`; a refusal for want of permission is a bare `403` with an empty
  `detail`.

## Upgrade notes
- Run `drush updb` (the role update) and `drush cr`.
- **Who can now delete what:** an app token (and so the Vinculum app) can delete the signed-in user's *own*
  inspections and queen observations, where the user could already delete them on the website. Check the role
  `hivelog_field_app` if you have changed it: a site's own additions are kept, nothing is revoked.
- **The override needs credentials in a header.** A browser session (cookies) gets nothing new, because a form
  on another site cannot set the `Authorization` header.
- **A host firewall that also blocks `X-HTTP-Method-Override`** would still stop edits; the app then says the
  host refuses it. The live host passes the header (probed), but PHP receiving it is proven only after this
  release is installed there: the first live edit is the test.
- The app uses `method_override` from the Vinculum build that includes edit and delete (1.1); an older app
  simply never sends one, and a newer app against a server older than this one tries a real `PATCH` or
  `DELETE` and says so if a firewall refuses it (asking for HiveLog 2.13).

- **OAuth key paths:** after upgrading the live (shared) host, sign-in failed with "You need to set the OAuth2
  private key." because the key files could no longer be read by their physical path. Setting
  `simple_oauth.settings` `private_key` and `public_key` to `private://...` paths fixed it, with no new keys needed. Use `private://` on a shared host, and when copying configuration between environments
  (DDEV to a live site): the configuration carries the paths, not the files. See the README's "OAuth keys"
  section. Nothing in HiveLog's code changed for this.
