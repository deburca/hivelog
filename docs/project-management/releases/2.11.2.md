# Release 2.11.2

A fix for the Vinculum app's hive page (task 0216), and a demo-site kit (task 0215) that is not
part of the module.

## Highlights
- **The app's hive page now shows the sensor tiles.** The `hivelog_field_app` role, which caps
  what an app token can do, had no sensor permission, so `/computed/hive/{hive}/stat-tiles`
  returned no tiles for any beekeeper on any site: no weight, no temperature, no net colony
  weight. The role now holds exactly two sensor permissions, `view own sensor device` and
  `view own sensor reading`, and nothing else about sensors (no add, edit, delete or "any").
  Sensors are still not on the API's allow-list: they stay a 404 as resources, and are readable
  only as those computed tiles. Another beekeeper's hive is still refused.
- The permissions are granted only where `nanoprobe` defines them. If `nanoprobe` is installed
  after `hivelog_api`, the role is topped up then; `hivelog_api_update_10002()` does it for an
  existing site and never revokes a change a site made.
- **`demo/`** is a DDEV kit for a throw-away demo site (for App Review and demonstrations of the
  app): `ddev demo-setup`, `demo-reset`, `demo-info`, invented records owned by a reviewer
  account, and `check.py`, which exercises the real OAuth flow end to end. It is excluded from
  the Composer package and changes nothing on a site that installs HiveLog.

## Schema / update hooks
- `hivelog_api_update_10002()`: tops up the field-app role with the two sensor view permissions
  (a no-op without `nanoprobe`). No entity schema changes.

## Upgrade notes
- Run `drush updb` (the role update) and `drush cr`.
- **Who can now see what:** a token can read the signed-in user's *own* sensors, through the
  tiles and through the web routes the user could already open; the access handlers still scope
  "own" to the apiary owner or a beekeeper member. Nothing can be written.
- Only matters if `nanoprobe` is enabled. Without it nothing changes.
