# Release 2.10.0

Two additions to the optional `hivelog_api` submodule for the iOS app (task 0205):
a fix that makes filtering work, and a schema endpoint. Nothing changes unless you
have enabled `hivelog_api`.

## Highlights
- **Fix: every filtered request on the API came back empty.** For a request with a
  `filter` parameter, JSON:API adds a condition that is always false unless a module
  says filtering across the record type is safe, and HiveLog had never said so, so
  only users with `administer hivelog` got results. An app asking "this hive's active
  queen" or "this hive's latest inspections" got nothing. HiveLog now says so for the
  exposed record types on `/hivelog/api/v1` only; those queries are already narrowed to
  the records the user may view, so a filter can only choose among them. Tests prove a
  filter cannot be used to probe another user's records (including through a
  relationship such as `filter[hive.name]`), that filtering by owner only matches the
  user themself, and that plain `/jsonapi` is unchanged.
- **New: `GET /hivelog/api/v1/schema`.** For each exposed record type, its writable
  fields with the kind of control to use, the label, whether it is required, its limits
  and, for a choice, the allowed values with their labels. JSON:API itself says nothing
  about allowed values, and a form that hard-codes them goes stale. The lists come from
  the entity definitions, so they are the ones the server validates against; a test
  submits every offered option of every type and expects it accepted.

## Upgrade notes
- **Only affects a site that has enabled `hivelog_api`.** Core HiveLog is unchanged.
- A client that worked around empty filtered results by fetching everything and
  filtering itself can now filter on the server.
- Field labels in the schema follow the interface language; the labels of allowed
  values are the untranslated strings in the entity definitions.
- Run `drush cr` after upgrading (a new route).
